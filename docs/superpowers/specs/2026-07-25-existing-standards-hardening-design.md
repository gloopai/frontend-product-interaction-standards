# 现有前端产品交互规范加固设计

## 背景

仓库当前包含 Dialog、Drawer、可搜索单选 Select / Combobox，以及响应式与自适应四类规范。单篇规范已具备较完整的状态、键盘、ARIA、跨端和验收要求，但随着 Select 与 Drawer、Dialog 与 Drawer 等交叉规则增加，需要系统检查跨文件冲突、遗漏、歧义和重复漂移风险。

本轮只加固现有规范，不增加表单、表格或其他新交互类别。

## 目标

1. 建立覆盖四份参考规范的交叉审计矩阵。
2. 检查专项规则和跨端转换规则能否同时成立。
3. 通过端到端场景确认状态、焦点、关闭、动画和清理形成闭环。
4. 只修复有证据的问题，并为每项硬性规则保留可操作的验收方法。
5. 保持文档职责清晰，避免同一完整规则在多个文件中复制。

## 非目标

- 不新增表单、表格、Toast、导航、上传等规范类别。
- 不规定 React、Vue、CSS 框架或组件库的具体实现。
- 不在缺少真实组件的情况下声称完成浏览器、屏幕阅读器、触控设备或视口实测。
- 不为了统一措辞而进行与问题无关的大范围改写。

## 审计方法

采用“交叉矩阵为主、端到端场景复核为辅”的方法。

### 交叉矩阵

以四份参考规范为列，按以下维度逐项核对：

| 维度 | 核对内容 |
| --- | --- |
| 生命周期 | 打开、活动、提交、失败、关闭、卸载、再次打开 |
| 关闭路径 | 关闭按钮、取消、确认、Escape、遮罩、手势、外部关闭 |
| 焦点与键盘 | 初始焦点、焦点陷阱、active、Tab、焦点返回、多层叠加 |
| 模态边界 | 背景隔离、页面滚动锁、遮罩覆盖、层级、活动实例唯一性 |
| 布局与滚动 | 固定区域、内容滚动、视口限制、虚拟键盘、安全区域 |
| 动画 | 初次打开、关闭、实时形态转换、动画期间保护、reduced motion |
| 业务状态 | 已提交值、草稿、错误、loading、失效值、请求和回调 |
| 跨端转换 | Dialog 与 Drawer、Select 浮层与 Drawer、断点和输入能力变化 |
| 无障碍 | 角色、名称、ARIA 所有权、状态播报、隐藏节点暴露 |
| 清理与恢复 | 路由变化、卸载、关闭完成、再次打开、旧请求和副作用 |
| 验收与报告 | 可执行检查、例外条件、未验证项的明确报告 |

每个发现归入以下一种类型：

- **明确冲突**：两条适用规则要求不兼容的行为。
- **规则缺口**：关键状态或转换没有确定结果。
- **表述歧义**：合理实现者可能得到不同结论。
- **重复漂移风险**：同一完整规则在多个文件维护，且边界或措辞可能分叉。

### 事实来源与冲突处理

- Dialog 专属几何、动画和模态行为以 `references/dialogs.md` 为事实来源。
- Drawer 专属方向、几何、动画和模态行为以 `references/drawers.md` 为事实来源。
- Select 的提交值、搜索草稿、active option、placement、Listbox 和 Combobox 语义以 `references/selects-comboboxes.md` 为事实来源。
- 跨断点的能力一致性、单实例转换和状态连续性以 `references/responsive-adaptive.md` 为事实来源。
- 兼容规则同时执行。形态专属规则发生冲突时，不使用笼统的“更严格者优先”，而是根据初次渲染、实时转换或关闭阶段明确指定事实来源。

## 端到端复核场景

至少静态推演以下场景：

1. Dialog 在打开期间由宽屏转换为 Drawer，再切回 Dialog。
2. 可搜索 Select 从 PC 浮层转换为 Drawer，并在存在 query、active、loading 或 error 时切换。
3. 多层 Dialog、Drawer 或混合叠加，逐层关闭并恢复焦点。
4. 异步提交期间触发 Escape、内部关闭操作、断点变化、路由变化或组件卸载。
5. 虚拟键盘、低高度、200% 缩放、四向安全区域和 reduced motion 下保持内容及操作可达。
6. 已提交 option 成为 orphaned invalid，远程搜索结果竞态，以及会话进入或离开 `none`。
7. 关闭动画尚未结束时发生重复关闭、重新打开或形态变化。

每个场景检查：

- 业务状态是否按提交边界保留或丢弃。
- 是否始终只有一个活动实例、遮罩、请求、回调、焦点陷阱和滚动锁。
- 关闭路径及例外是否一致且对用户可解释。
- 焦点、背景隔离和页面滚动锁是否连续。
- 动画、卸载和清理是否只发生一次，且顺序明确。

## 修改原则

1. 先记录问题和受影响场景，再进行最小修订。
2. 专项完整规则只保留在对应 `references/*.md`；其他文件通过链接或边界说明引用。
3. `SKILL.md` 只维护触发路由、执行流程、全局原则和红线。
4. `README.md` 只维护用户可理解的能力摘要、安装和贡献信息。
5. 没有实质问题的文件不为制造一致外观而修改。
6. 新增或修改硬性规则时，同步补充对应的完成前检查或验收项。
7. 保持框架无关，只描述用户可观察行为、状态边界和验证结果。

## 预期产物

- 必要时修订四份参考规范。
- 必要时校准 `SKILL.md` 和 `README.md`。
- 审计结论：列出发现类型、受影响场景、修复位置和未修改原因。
- 验证记录：区分静态文档检查、规则推演和真实交互验证。

## 验证方案

### 文档与结构验证

- 运行 Skill 官方结构和 YAML 校验。
- 检查 Markdown 相对链接均指向现有文件。
- 扫描未完成的占位标记。
- 检查术语、规则编号、事实来源和交叉链接是否一致。
- 运行 `git diff --check`。

### 规则验证

- 对修改后的四份规范重新执行交叉矩阵。
- 逐一静态推演端到端复核场景。
- 确认每项修订都有明确的失败条件和可操作验收方法。
- 确认没有将实现建议误写成普遍硬性产品规则。

### 验证边界

本轮是规范文档加固。除非另有真实业务组件和测试环境，不执行也不声称通过浏览器、屏幕阅读器、触控设备或真实视口测试。最终报告必须将这些项目标记为未验证，并说明应在具体组件实现阶段完成。

## 完成标准

- 交叉矩阵所有维度均完成审计，并且每个发现都有明确处置。
- 七类端到端场景均能从规范中得到唯一、无冲突的预期结果。
- 所有新增或修改规则都有对应验收方法。
- Skill、链接、占位符和 Git 差异检查通过。
- 最终报告准确区分已完成的静态验证与未执行的真实交互验证。

# 用户侧附件与内容提交上传交互规范设计

## 背景

现有 `references/uploads-imports.md` 已经覆盖文件选择、上传队列、上传进度、取消、重试、结构化导入、预检、字段映射和导入结果；`references/files-media-assets.md` 已经覆盖文件进入系统后的资产身份、预览、版本、分享、发布、删除恢复和使用关系。

但很多高频产品场景既不是管理台导入，也不是资产库管理，而是用户在一个业务动作里附带提交文件：头像、评论配图、聊天附件、工单附件、反馈截图、内容投稿封面、表单证明材料、语音消息、短视频、移动端相机/相册选择。这些场景最容易把“文件已选”“上传成功”“消息已发送”“内容已发布”“附件可见”“资产已入库”混成一个状态。

常见问题包括：发送按钮读取仍在上传中的本地文件；上传成功就清空编辑草稿但消息发送失败；聊天附件迟到结果写入下一条消息；删除发送前附件误删已发送附件；头像裁剪成功被当成头像已生效；移动端只有相机没有相册或只有拖拽没有选择文件；离开页面时没有说明本地草稿、上传任务和已发送内容各自会怎样；无权限或会话切换后旧附件预览、旧上传凭证、旧复制链接仍然可用。

因此下一阶段应新增独立 owner：用户侧附件与内容提交上传。它接管“附件作为一次用户内容提交的一部分”时的草稿、上传、提交、发送、发布、失败恢复和移动端输入体验，而不是重复定义通用上传队列或资产库生命周期。

## 目标

新增 `references/user-attachment-submission.md`，作为头像上传、资料图片、评论附件、聊天附件、工单附件、反馈附件、内容投稿附件、移动端拍照/录音/录像、发送前预览、发送后附件引用和附件草稿恢复的专属 owner。

该 owner 需要约束：

- 附件输入所属的内容草稿、消息草稿、评论草稿、工单草稿、反馈草稿、头像草稿和提交身份。
- 本地选择、压缩/裁剪/转码草稿、上传引用、提交 payload、发送结果、发布结果和资产入库结果的状态分层。
- 发送、提交、保存草稿、发布、撤回、删除附件、替换附件、重试上传、重试发送和离开页面的意图边界。
- 多附件、移动端相机/相册/文件选择、粘贴、拖拽、录音录像、弱网、后台切换和迟到结果的恢复。
- 权限、会话、租户/工作区、内容状态、上传凭证、附件可见性和旧预览/旧引用失效。

## 非目标

- 不替代 `uploads-imports.md` 的通用文件选择、上传队列、进度、取消、重试和导入预检规则；本 owner 会引用它作为底层上传会话规则。
- 不替代 `files-media-assets.md` 的资产库、文件详情、媒体预览、版本、分享链接、发布/下架和删除恢复规则。
- 不替代 `forms.md` 的字段级 dirty、touched、错误摘要和表单提交快照。
- 不替代 `complex-editors-builders.md` 的复杂编辑器、富文本编辑器、内容构建器和发布工作台规则。
- 不替代 `messages/notifications` 类系统通知规则；本 owner 只约束用户主动提交的内容附件。
- 不定义对象存储、图片压缩算法、视频转码算法、消息协议、聊天服务、内容审核策略或业务领域的文件类型政策。

## 方案比较

### 方案 A：扩展上传与导入 owner

优点是少一个文件，所有上传动作集中。缺点是用户内容提交会把上传 owner 拉向“消息发送、评论发布、头像生效、草稿恢复、撤回删除、移动端拍摄”这些业务语义，导致导入/上传规范变得过胖，也容易让上传成功被误读成业务提交成功。

### 方案 B：扩展文件与媒体资产 owner

优点是附件最终常常会成为资产，能复用预览、版本和权限规则。缺点是用户发送附件时，核心风险发生在“发送前草稿和发送结果”阶段，而不是资产库管理阶段。把它塞进资产 owner，会淡化本地草稿、迟到上传结果、发送失败恢复、移动端输入方式和内容提交快照。

### 方案 C：新增用户侧附件与内容提交上传 owner

优点是边界最清楚：Upload owner 管文件怎样上传；Asset owner 管文件入库后怎样管理；本 owner 管附件怎样绑定到一次用户内容提交，并确保发送/发布/保存草稿/失败恢复不会串状态。缺点是需要新增路由、README/HANDOFF 摘要、相邻 owner 关系和可执行审计。

推荐方案 C。它能覆盖用户侧高频风险，同时不影响现有管理台上传、结构化导入和资产管理规范。

## `attachmentSubmissionState`

每个用户侧附件提交场景必须声明 `attachmentSubmissionState`：

| 字段 | 含义 |
| --- | --- |
| `attachmentSubmissionOwnerId` | 当前附件提交实例身份，绑定内容草稿、消息/评论/工单/头像对象、会话、租户/工作区、权限版本和承载面。 |
| `contentDraftBinding` | 文本、富文本、表单字段、评论、消息、工单、头像、投稿或反馈草稿身份，以及附件与草稿的绑定关系。 |
| `inputSourcePolicy` | 允许的输入来源：文件选择、相机、相册、录音、录像、粘贴、拖拽、系统分享、重新选择和平台限制。 |
| `localAttachmentDrafts` | 本地文件、临时预览、裁剪/压缩/转码草稿、顺序、描述、替代文本、删除标记和本地错误。 |
| `uploadBinding` | 对应 Upload owner 的 `uploadSessionState`、文件项身份、上传凭证、上传引用、进度、失败、取消和迟到结果策略。 |
| `submitSnapshot` | 用户点击发送、提交、保存、发布或更新头像时冻结的文本、附件引用、权限版本、内容版本、幂等键和来源意图。 |
| `sendPolicy` | 发送/提交/保存/发布/更新头像的防重复、loading、未知结果、失败恢复、重试范围和回执 owner。 |
| `postSubmitState` | 发送后内容、评论、消息、工单、头像或投稿的可见状态、附件可见性、审核/扫描/转码状态和失败回滚。 |
| `revisionPolicy` | 发送前删除/替换/重排附件、发送后编辑、撤回、删除附件、重新上传、重新发送和版本冲突策略。 |
| `permissionBoundary` | 上传、预览、发送、查看、下载、编辑、撤回、删除和重试时的权限、会话、租户/工作区和旧状态收敛。 |
| `feedbackBinding` | Inline、字段错误、附件项错误、发送结果、弱网状态、Toast、Alert、Notification 和恢复入口的 owner。 |
| `responsivePolicy` | 移动端相机/相册、触摸排序、虚拟键盘、输入栏、底部操作、安全区域、后台切换和离线恢复策略。 |

`attachmentSubmissionState` 只负责附件如何参与一次用户内容提交。底层文件上传仍执行 `uploads-imports.md`；上传后成为资产、需要资产详情、分享链接或资产删除恢复时，继续执行 `files-media-assets.md`。

## 核心规则

### 附件草稿、上传引用和内容提交分层

选择文件、生成本地预览、完成裁剪/压缩、上传成功、发送成功、内容发布成功、头像生效和资产入库必须是不同状态。

发送、提交、保存、发布或更新头像只能读取当前 `submitSnapshot` 中允许的附件引用。仍在本地校验、裁剪、压缩、上传中、上传失败、引用过期或权限不可证明的附件不得进入有效提交 payload。上传成功只能说明文件引用可用于当前提交候选；不能自动说明消息已发送、评论已发布、头像已生效、内容已审核通过或资产已入库。

### 发送按钮和附件队列的关系

发送按钮不得只读取“是否有本地文件名”。它必须根据文本草稿、附件草稿、上传状态、必填规则、权限、会话、内容版本和提交策略计算可用性。

如果产品允许边上传边发送，必须明确 `sendPolicy`：发送时冻结附件项身份和上传引用候选，后续上传失败、迟到结果或用户删除附件不能静默改写已发送请求。若产品要求全部上传完成后才发送，未完成附件必须阻止提交并提供文件级原因和恢复动作。

重复点击、Enter、快捷发送、触摸、拖拽完成回调、自动重试和离线恢复都必须复用同一幂等身份或被拒绝，不能生成重复消息、重复评论、重复工单、重复头像更新或重复投稿。

### 迟到结果、替换和删除

本地文件 A 被替换为文件 B 后，A 的裁剪、压缩、上传或扫描迟到结果不得写入 B。上一条消息、上一条评论、旧工单草稿或旧头像裁剪的迟到结果不得写入当前草稿。

发送前删除附件只删除当前草稿的附件项和上传候选；发送后删除附件、撤回附件或编辑附件必须声明影响内容版本、附件可见性、审计、接收方已读状态、通知状态和恢复边界。删除请求发送不等于所有接收方、缓存、缩略图、下载链接或通知都已收敛。

### 头像、封面和内容配图

头像上传、封面上传和内容配图必须区分选择、裁剪、预览、上传、保存、生效、审核、缓存刷新和旧图片失效。裁剪成功不等于头像已生效；保存请求发送不等于所有页面、通知、评论头像、历史消息头像或 CDN 已刷新。

头像/封面更新失败时，不能只 Toast 后关闭裁剪器；必须保留可恢复草稿或明确说明草稿是否已丢弃。旧头像、旧封面、旧缩略图、旧 ARIA label、旧焦点目标和旧复制链接在权限、会话、版本或更新结果变化后必须失效或重新证明安全。

### 消息、评论、工单和反馈附件

消息、评论、工单和反馈附件必须绑定到对应内容草稿和发送请求。文本发送成功但附件失败、附件上传成功但文本发送失败、部分附件失败、内容进入审核、服务端未知结果、离线队列等待发送和接收方无权查看附件都必须是可区分状态。

发送后附件如果需要扫描、转码、审核或安全处理，内容可以先进入等待附件处理状态，但不能展示为附件完全可见。部分附件不可见时，必须说明哪些附件成功、失败、处理中、无权、过期或被拦截，并提供重试、删除、重新选择、查看原因或联系支持路径。

### 权限、会话和隐私

权限不足、会话过期、账号切换、租户/工作区切换、内容被删除、工单关闭、评论区锁定、用户被禁言、附件能力关闭或上传凭证过期时，旧本地预览、旧上传引用、旧发送按钮、旧重试入口、旧下载入口、旧缩略图、旧复制内容、旧焦点目标和旧 ARIA 引用必须失效或重新证明安全。

无权或未启用时，附件选择、相机/相册、录音录像、粘贴、拖拽、预览、上传、发送、重试、删除、撤回、下载和查看原图的 DOM、state、handler、request 和快捷键入口为 0。

附件预览、文件名、缩略图、EXIF、语音时长、视频时长、地理位置、内部 ID、下载链接、错误明细和旧缓存都不得在无权限、被删除、已撤回、被审核拦截或会话失效状态下泄露。

### 移动端和弱网承载

移动端不得删除相机、相册、文件选择、录音录像、附件预览、文件级错误、上传进度、删除/替换、重试、发送状态、离开保护、权限原因、失败恢复和已发送附件状态。

移动端可以把附件选择、预览、裁剪、排序、添加描述、替代文本、压缩选项和失败明细放入 Bottom Sheet、全屏 Drawer、独立页或分步流程，但必须保留同一个 `attachmentSubmissionState`、同一个草稿身份、同一个上传队列、同一个提交快照和同一个恢复策略。

虚拟键盘、输入栏吸底、安全区域、弱网、离线、App 后台切换、系统文件选择器返回、相机权限拒绝、录音权限拒绝和横竖屏切换后，文本草稿、附件草稿、上传进度、错误、焦点和发送按钮状态不能丢失或错绑。

### 反馈、可访问性和恢复

附件错误不能只挂在缩略图红框或 Toast。文件类型不符、大小超限、数量超限、上传失败、扫描失败、发送失败、未知结果、无权、过期和审核拦截必须有可访问文本、文件级定位和恢复动作。

同一完整错误消息只能由一个 primary owner 播报；不能同时在附件项、输入栏、Toast 和全局 live region 中重复播报。附件删除、重试、发送、撤回和重新上传按钮必须有动作对象，例如“删除 截图 1”“重试 发票.pdf”“撤回 语音消息”。

离开页面、关闭 Dialog/Drawer、刷新、返回上一页或切换账号时，必须说明本地草稿、上传中附件、已上传未发送附件、已发送内容和后台任务分别如何处理。无法安全保存草稿时，必须阻止或确认离开。

## 与现有 owner 的关系

- `uploads-imports.md`：负责底层文件选择、上传队列、上传进度、取消、重试、文件项身份和迟到上传结果；本 owner 负责这些上传结果如何进入用户内容提交。
- `files-media-assets.md`：负责附件成为资产后的预览、版本、分享、发布、删除恢复和使用关系；本 owner 负责发送前草稿、发送结果和内容附件绑定。
- `forms.md`：表单证明材料、头像字段、资料图片和反馈表单附件同时执行 Form owner 的字段状态、提交快照、错误摘要和未保存离开。
- `complex-editors-builders.md`：内容投稿、富文本插图、Markdown 图片、模板附件和复杂编辑器中的素材草稿同时执行复杂编辑器 owner。
- `buttons.md`：选择文件、拍照、录音、删除附件、替换、重试、发送、撤回和提交按钮继续执行 Button owner。
- `overlays-menus-tooltips.md`：附件更多菜单、预览浮层、Action Sheet、Tooltip 和移动端菜单承载继续执行浮层 owner。
- `risk-actions.md`：撤回已发送附件、删除已发送附件、公开可见附件、跨租户附件、敏感证明材料和不可恢复删除继续执行风险 owner。
- `permissions-tenancy-visibility.md`：权限、会话、租户/工作区、只读、隐藏、禁用、未启用和无泄露继续执行 Permissions。
- `feedback-states.md` 与 `global-feedback.md`：附件错误、弱网、未知结果、发送结果和恢复入口继续执行反馈 owner；Toast 不能作为唯一回执。
- `responsive-adaptive.md`：移动端相机/相册、虚拟键盘、输入栏吸底、触摸排序、安全区域、弱网和后台切换继续执行响应式规则。

## 可执行审计设计

新增 `docs/testing/user-attachment-submission/user-attachment-submission-audit.rb`，采用现有 Ruby 静态审计模式。

审计需要验证：

1. owner 文件存在，且包含 `attachmentSubmissionState` 与全部状态字段。
2. `SKILL.md` 包含头像上传、评论附件、聊天附件、工单附件、反馈附件、内容投稿、发送图片/文件/语音/视频、拍照上传、相册选择、粘贴图片、附件草稿、发送前预览、撤回附件等中英文触发词。
3. `README.md` 与 `HANDOFF.md` 只保留摘要和 owner 链接，不复制完整规则。
4. RED/GREEN 证据覆盖文件已选即发送、上传成功即内容成功、头像裁剪即生效、发送按钮读取本地文件名、迟到结果写入新草稿、发送前删除误删已发送附件、移动端删除相机/相册/重试/离开保护、无权入口未清零、Toast-only 附件错误、运行时验证伪装已通过和项目专属泄漏。
5. owner 不包含业务项目路径、客户名、具体框架、组件库或消息服务例外。

## 验收清单

- 每个用户侧附件提交场景声明 `attachmentSubmissionState` 全字段。
- 选择文件、生成本地预览、完成裁剪/压缩、上传成功、发送成功、内容发布成功、头像生效和资产入库分开表达。
- 发送、提交、保存、发布或更新头像只读取当前 `submitSnapshot` 中允许的附件引用。
- 上传中、上传失败、引用过期或权限不可证明的附件不得进入有效提交 payload。
- 发送按钮绑定文本草稿、附件草稿、上传状态、必填规则、权限、会话、内容版本和提交策略。
- 迟到裁剪、压缩、上传、扫描或发送结果不能写入新草稿、新消息、新评论、新工单或新头像。
- 发送前删除附件、发送后删除附件、撤回附件和编辑附件分开表达。
- 头像/封面选择、裁剪、预览、上传、保存、生效、审核、缓存刷新和旧图片失效分开表达。
- 消息/评论/工单/反馈附件区分文本成功附件失败、附件成功文本失败、部分附件失败、审核中、未知结果、离线队列和接收方无权。
- 无权或未启用时，附件选择、相机/相册、录音录像、粘贴、拖拽、预览、上传、发送、重试、删除、撤回、下载和查看原图的 DOM、state、handler、request 和快捷键入口为 0。
- 移动端保留相机、相册、文件选择、录音录像、附件预览、文件级错误、上传进度、删除/替换、重试、发送状态、离开保护、权限原因、失败恢复和已发送附件状态。
- 未执行真实浏览器、真实移动端设备、相机/相册/录音权限、真实上传、真实弱网/离线、真实后台切换、键盘、触摸和读屏检查时，必须标为未验证。

## 自检结论

本设计聚焦单一 owner：用户侧附件与内容提交上传。它不替代通用上传、结构化导入、文件资产管理、表单或复杂编辑器，而是定义附件参与一次用户内容提交时的草稿、上传引用、提交快照、发送结果、失败恢复、权限收敛和移动端输入边界。文档没有引入具体业务项目、组件库、框架或消息服务例外；真实浏览器、移动端设备、相机/相册/录音权限、真实上传、弱网/离线、后台切换、键盘、触摸和读屏验证明确留到业务实现阶段。

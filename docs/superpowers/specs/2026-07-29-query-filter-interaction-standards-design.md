# 查询条件与筛选交互规范设计

## 背景

当前 `data-tables.md` 已覆盖表格查询快照、已应用筛选、排序、分页、请求代次和结果状态；`forms.md` 覆盖字段值、校验、dirty/touched 和提交生命周期；`selects-comboboxes.md` 覆盖 Select 内部草稿、搜索和已提交值。但业务项目里最高频的“查询条件区”仍容易被做坏：搜索框输入即请求、筛选草稿直接改结果、清空和重置语义混乱、URL 丢状态或泄露敏感值、默认条件不可见、移动端筛选被删掉、折叠条件不可发现、刷新/返回后条件无法复现。

这些问题往往发生在列表、报表、审计日志、任务中心、文件管理和管理台记录页。它们看起来像表格局部逻辑，但根源是查询条件区缺少独立 owner：它既不是普通表单提交，也不是表格分页排序本身，而是“用户如何形成可复现的查询意图”。

本设计新增 `references/query-filters.md`，作为搜索、筛选和查询条件区的唯一事实来源。它负责查询条件草稿、应用、重置、URL 同步、敏感值、安全、移动端承载和结果关系；表格 owner 继续接收已应用查询快照并负责结果、分页、排序和选择。

## 目标

- 新增 `references/query-filters.md`，覆盖关键词搜索、筛选条件区、条件草稿、应用/重置/清空、已应用条件摘要、URL 同步、默认值、请求时机和移动端承载。
- 明确 `filterDraft`、`appliedFilters`、`defaultFilters`、`queryIntent`、`urlState` 和 `sensitiveFilters` 的状态边界。
- 约束 immediate 与 explicit 两种应用模式：简单低成本条件可即时应用，多字段、昂贵、敏感或需要组合确认的条件必须显式应用。
- 防止 URL 泄露敏感值、浏览器返回状态不可复现、折叠筛选不可发现和移动端删除核心条件。
- 与 Data Table、Form、Select、Button、Dialog/Drawer、Admin Console、Responsive owner 明确组合，避免重复或冲突。
- 建立 RED/GREEN 文档压力测试和结构化审计，确保常见筛选违规形态可被抓住。

## 非目标

- 不重新定义表格排序、分页、列、选择、批量操作或结果状态；这些仍由 `data-tables.md` 负责。
- 不重新定义字段校验、dirty/touched、错误摘要或提交生命周期；这些仍由 `forms.md` 负责。
- 不重新定义 Select / Combobox 内部搜索草稿、弹层、active option 或提交值；这些仍由 `selects-comboboxes.md` 负责。
- 不覆盖全站搜索、命令面板、智能搜索语法、高级查询语言编辑器、BI 自由分析器或自然语言查询。
- 不规定框架、路由库、URL 序列化库、组件库 API 或视觉 token。

## 推荐方案

采用独立 Query Filter owner，聚焦“查询条件区如何形成已应用查询意图”。

### 方案对比

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 独立 `query-filters.md` owner | 能统一草稿/应用/重置/URL/移动端/敏感值；适用于表格、卡片列表、报表和审计页。 | 需要新增路由、摘要和审计，并与 Data Table 边界写清楚。 | 推荐。 |
| 继续扩展 `data-tables.md` 的筛选章节 | 少一个文件；表格场景直接。 | 查询条件区不只用于表格；Data Table 文件已经很重，继续塞会模糊 owner。 | 不采用。 |
| 把筛选看作普通表单写入 `forms.md` | 能复用字段状态。 | 查询请求、URL 同步、默认筛选、已应用摘要和返回复现超出普通表单职责。 | 不采用。 |

## 首版范围

首版覆盖：

- 列表、表格、报表、审计日志、任务中心和管理台记录页的查询条件区。
- 关键词搜索、普通筛选、日期范围、状态、分类、租户/工作区可见条件、标签、负责人、时间窗口和更多筛选。
- `immediate` 和 `explicit` 应用模式。
- 默认筛选、重置、清空、单项移除、折叠筛选摘要和已应用条件 chips。
- URL 可复现、安全序列化、浏览器返回/前进、分享链接和刷新恢复。
- PC、移动端、触摸、键盘、低高度、虚拟键盘、安全区域和辅助技术可达性。

暂不覆盖：

- 全站搜索页、命令面板、IDE 式复杂查询语言、SQL/DSL 编辑器。
- AI 自然语言检索、语义搜索排序和推荐算法。
- BI 拖拽分析器、交叉透视和自由维度建模。
- 具体组件库实现。

## 核心设计

### 1. 查询条件状态模型

每个查询条件区维护 `queryFilterState`：

| 字段 | 语义 |
| --- | --- |
| `filterOwnerId` | 当前条件区稳定身份。 |
| `filterDraft` | 用户正在编辑、尚未应用到结果的业务条件草稿。 |
| `appliedFilters` | 已应用到结果、URL、标题、结果摘要和请求快照的条件。 |
| `defaultFilters` | 产品声明的默认条件；重置恢复它，而不是含糊清空。 |
| `filterSchema` | 每个条件的类型、应用模式、默认值、敏感性、URL 策略、权限和可见性。 |
| `queryIntent` | 本次应用、移除、重置、刷新或返回恢复形成的查询意图。 |
| `urlState` | 可安全序列化到 URL 的已应用条件和版本。 |
| `requestBinding` | 交给结果 owner 的查询快照引用、权限版本和请求代次。 |

`filterDraft` 与 `appliedFilters` 必须分离。用户输入、打开 Select、修改日期范围、勾选选项或展开更多筛选，只能改变草稿；只有被声明为 `immediate` 且已提交合法业务值，或用户触发“应用”，才形成新的 `appliedFilters`。

### 2. 应用模式

每个条件声明 `applyMode: immediate | explicit`。即时模式适用于低成本、单字段、无强组合依赖、不会造成明显请求压力的条件；显式模式适用于多字段组合、日期范围、复杂 Select、远程选项、昂贵请求、敏感条件、会重置选择或会影响批量范围的条件。

即时模式也不能把字段内部草稿当业务值：关键词搜索需要最小输入策略、防抖和提交边界；Select 只能在其 owner 提交 `selectedValue` 后应用；日期范围两端合法且完整后才可应用。显式模式中，结果、URL、数量和标题只反映 `appliedFilters`，不能在用户编辑草稿时假装已生效。

### 3. 重置、清空和移除

“重置”恢复 `defaultFilters`；“清空”移除所有可清空的非强制条件；“移除单项”只移除该已应用条件。三者必须文案不同、结果不同、URL 更新不同。若产品只有默认条件，不得把“重置”写成清空所有条件；若有权限/租户强制条件，它们不能被清空。

已应用条件必须持续可见或在摘要中可发现。折叠区域内的条件如果已经应用，折叠头必须显示数量、摘要或 chips，不能让用户看不到为什么结果被过滤。

### 4. URL、返回和可复现

只有明确 `urlSafe` 的已应用条件可以进入 URL。账号、令牌、个人识别、敏感自由文本、内部权限范围和产品标记 `sensitive` 的条件不得进入路径、查询串、片段、标题、日志或 analytics。不可 URL 化但需要恢复的条件可以存在于会话状态，但分享链接必须明确不包含它们。

页面初始化、刷新、浏览器前进/后退和打开分享链接时，必须按版本化 `urlState` 解析条件：合法且可用的值进入 `appliedFilters`；过期、无权限、无效或已删除选项进入可见失效状态，并提供移除、替换或回到默认条件路径。不得静默忽略 URL 中的已知条件，也不得把无效条件伪装成成功过滤。

### 5. 请求时机和结果绑定

查询条件区只负责形成查询意图；结果 owner 负责请求、结果、分页、错误和刷新。每次应用、移除、有效重置、URL 恢复或显式刷新时，条件区输出不可变 `queryIntent`，结果 owner 再冻结完整查询快照。

应用条件时，页码分页回到第 1 页，游标分页回到初始游标；已有选择、批量范围和行操作快照按 Data Table owner 失效。正在编辑草稿时不得发请求；重复点击“应用”、键盘重复提交或事件重放不得形成多个等价 queryIntent。

### 6. 权限、安全和管理台边界

权限、租户/工作区、角色或数据范围变化时，条件区必须重新解析 `filterSchema`、可见条件、默认条件和已应用条件。无权条件、敏感值、旧租户选项和旧 URL 状态不能继续暴露。权限不足状态应解释恢复路径，但不得泄露敏感对象名称、数量或字段。

管理台审计日志、权限列表、任务中心和导入导出页面的条件区必须把权限版本、租户/工作区和数据范围写入 queryIntent；导出或批量操作读取的是已应用条件和结果 owner 的查询快照，不得读取正在编辑的草稿。

### 7. 响应式与可访问性

PC 上查询条件区可展示主条件和折叠的更多筛选；移动端可用 Drawer 或独立筛选页承载复杂筛选。但核心能力不能删除：查看已应用条件、编辑条件、应用、重置/清空、单项移除、查看错误和返回结果都必须可达。

筛选字段必须有可见 label 或等价可访问名称；错误和帮助文本关联到字段；已应用条件 chips 有可访问名称和移除按钮；“应用”和“重置/清空”按钮有动作对象。虚拟键盘、低高度、200% 缩放和安全区域下，当前编辑条件、错误、应用按钮和取消/返回路径不得被遮挡或删除。

## 与现有 owner 的关系

- `data-tables.md`：表格 owner 接收 `appliedFilters` 形成查询快照，并负责排序、分页、结果、选择和批量失效；Query Filter owner 负责草稿、应用、重置、URL 和条件摘要。
- `forms.md`：筛选字段 label、校验、错误关联和字段状态复用 Form 原则；但筛选条件区不是普通业务保存表单，不产生记录提交。
- `selects-comboboxes.md`：Select 的 query、active option、popup 状态不进入 `filterDraft` 或 `appliedFilters`；只有明确提交的业务值才能成为筛选条件。
- `buttons.md`：应用、重置、清空、移除条件、打开更多筛选和移动端筛选按钮遵循按钮文案、层级、loading、防重复和禁用原因。
- `dialogs.md` / `drawers.md`：移动端筛选 Drawer 或高级筛选 Dialog 的遮罩、关闭、焦点陷阱、滚动和 disposal 由容器 owner 管理。
- `admin-console.md`：权限、租户/工作区、敏感筛选、审计日志、导出和批量操作读取管理台 owner 的安全边界。
- `responsive-adaptive.md`：断点、触摸、虚拟键盘、安全区域和折叠策略由响应式 owner 管理；Query Filter 声明条件能力不得消失。

10. 响应式、移动端和可访问性
11. 可执行验收

稳定规则族建议：

- `QF-SCOPE-*`：范围、非目标和术语。
- `QF-STATE-*`：`queryFilterState`、草稿、已应用、默认值和 schema。
- `QF-APPLY-*`：immediate / explicit、请求意图、防重复和字段提交边界。
- `QF-RESET-*`：重置、清空、移除和强制条件。
- `QF-SUMMARY-*`：已应用条件摘要、chips、折叠和可发现性。
- `QF-URL-*`：URL 安全序列化、版本、返回恢复和敏感值。
- `QF-PERM-*`：权限、租户、无权条件和安全收敛。
- `QF-A11Y-*`：label、错误、按钮名称、chips 和状态公告。
- `QF-RSP-*`：移动端、Drawer/独立页、虚拟键盘和安全区域。

## 测试与验证策略

采用 RED/GREEN 文档压力测试：

- RED：在没有 Query Filter owner 的情况下，让 fresh 输出用户列表、审计日志、任务中心、报表筛选和移动端筛选设计，记录是否出现输入即请求、草稿直接改结果、重置清空混淆、URL 泄露敏感值、折叠条件不可发现、移动端筛选能力消失等问题。
- GREEN：启用 owner 后，同样任务必须声明 `queryFilterState`、草稿/已应用分离、应用模式、默认值、重置/清空差异、已应用摘要、URL 安全、权限复核、移动端承载和运行时验证边界。
- 审计脚本：检查 owner 规则、路由、状态字段、immediate/explicit、defaultFilters、urlSafe、sensitive、重置/清空语义、折叠摘要、移动端可达和未验证边界。

关键 mutation：

- 删除 `filterDraft` 与 `appliedFilters` 分离，必须失败。
- 把字段内部草稿直接写入结果或 URL，必须失败。
- 未声明 applyMode 就自动输入即请求，必须失败。
- 把重置写成清空所有条件，必须失败。
- 删除已应用条件摘要或折叠条件数量，必须失败。
- 把 sensitive 条件序列化到 URL，必须失败。
- 浏览器返回时静默忽略无效 URL 条件，必须失败。
- 权限变化后继续显示旧筛选值或旧选项，必须失败。
- 移动端删除筛选、应用、重置或已应用摘要，必须失败。
- 把浏览器/移动端/辅助技术运行时写成已验证，必须失败。

## 验收标准

- Query Filter owner 首版范围清晰，覆盖列表查询条件区、搜索、筛选、URL、默认值、移动端和权限边界。
- 与 Data Table、Form、Select、Button、Dialog/Drawer、Admin Console 和 Responsive owner 边界不冲突。
- README/HANDOFF/SKILL 只做摘要和路由，不复制 owner 细节。
- RED/GREEN 输出和审计 mutation 能覆盖核心反例。
- 未执行浏览器、屏幕阅读器、触摸设备或真实组件运行时时，所有证据必须标为未验证。

# 状态流转与记录生命周期交互规范设计

## 背景

管理台里大量对象都有生命周期：启用/停用、发布/下线、审批/驳回、归档/恢复、冻结/解冻、锁定/解锁、草稿/已发布、待审核/已通过/已拒绝、运行中/暂停中/已完成。这些能力现在散落在按钮、危险操作、权限、异步任务、审计日志、信息展示和表格规范里，但还缺少一个独立 owner 来回答三个关键问题：

- 当前状态能否被理解、比较和恢复？
- 从状态 A 到状态 B 的操作边界是什么？
- 变更结果如何证明成功、失败、冲突、异步处理中或未知？

没有生命周期 owner 时，常见错误包括：把状态 badge 当成状态机、把按钮 loading 当成已流转、乐观更新直接覆盖真实状态、冲突后仍显示旧状态、移动端删掉状态原因和恢复路径、批量状态变更只用 Toast 表达结果、无权限时泄露对象状态和下一步动作。

## 目标

- 新增 `references/status-lifecycle-transitions.md` 作为状态流转、记录生命周期和状态机交互的唯一事实来源。
- 明确 `lifecycleState`、`transitionIntent`、`transitionPolicy`、`transitionResult`、`versionSnapshot`、`permissionBoundary`、`auditReceipt` 和 `recoveryPolicy` 等核心状态。
- 区分状态展示、状态变更、状态预览、乐观更新、异步处理中和最终结果。
- 约束状态流转必须绑定对象版本、权限版本、租户/工作区、影响范围、确认策略、请求身份和审计回执。
- 覆盖冲突、过期、部分成功、未知结果、异步任务、批量状态变更、权限变化和移动端承载。

## 非目标

- 不定义后端状态机、工作流引擎、审批引擎或数据库版本策略。
- 不替代危险操作、权限、审计日志、按钮、表格、异步任务或信息展示 owner；这些仍按各自规则执行。
- 不规定某个业务项目的状态枚举、审批角色、按钮文案或接口字段。
- 不把所有状态变更都强制做成危险操作；只有影响范围、不可逆性、权限或外部系统风险达到条件时才转交危险操作 owner。

## 设计方案

### 状态模型

每个可被展示或变更生命周期的对象必须声明 `lifecycleState`。它至少描述当前状态、可见状态标签、状态来源、状态版本、可用转移动作、权限边界、业务限制、异步占用、冲突策略、审计回执和恢复路径。

状态展示和状态变更分离。只读状态 badge 只能展示当前已证明状态；hover、focus、预览、草稿、loading、乐观状态和本地禁用不能伪装成已提交生命周期。

### 转换意图与提交

每次启用、停用、发布、下线、审批、驳回、归档、恢复、冻结、解冻、锁定、解锁或类似状态变更都必须创建 `transitionIntent`。它冻结对象 ID、对象版本、当前状态、目标状态、权限版本、租户/工作区、影响范围、确认策略、请求身份和来源 owner。

提交请求只能读取已冻结的 `transitionIntent`。若对象版本、权限版本、租户/工作区、当前状态或业务限制在确认前变化，旧意图必须失效并要求重新确认或重新加载。

### 结果与恢复

状态变更结果不能只靠按钮恢复、Toast 或局部 badge 更新表达。`transitionResult` 必须区分 success、failure、partial-success、conflict、stale、unknown、queued、processing 和 cancelled-client-only。

客户端关闭 Dialog、Drawer、Toast、页面或浏览器 Tab 不能写成服务端状态已取消。异步状态变更必须进入任务中心或可恢复结果 owner；未知结果必须提供检查状态、刷新、查看任务、查看审计或联系支持路径。

### 权限、安全与审计

状态流转必须复核权限、租户/工作区、对象版本和可用转移动作。无权限不得泄露当前状态、下一步动作、不可见原因、对象数量、批量影响范围、审批意见、拒绝原因、内部状态码、任务结果或旧缓存。

成功、失败、部分成功、冲突、未知和异步完成都必须能关联审计回执或明确标为审计未验证。高风险状态变更转交危险操作 owner；批量状态变更读取表格选择快照和筛选快照。

### 移动端与可访问性

移动端可以折叠低频状态说明或把复杂状态变更放入 Drawer / Bottom Sheet / 独立页，但不得删除当前状态、状态原因、可用动作、禁用原因、确认、结果回执、审计入口或恢复路径。

状态和转移动作不能只靠颜色、图标、位置、hover 或 tooltip 表达。状态变化、冲突、异步处理中、未知结果和恢复成功必须由唯一 owner 公告，并保证焦点只迁移一次。

## 硬性红线

- 状态 badge、按钮 loading、乐观 UI、Toast 文案或本地缓存不得伪装成已完成状态流转。
- 状态展示和状态变更不得共用一个含糊 `status` 字段；必须区分当前已证明状态、目标状态、草稿/预览、处理中和结果。
- 没有冻结对象版本、权限版本、当前状态、目标状态、租户/工作区和请求身份，不得提交状态变更。
- 版本冲突、权限变化、租户切换、对象删除、状态已变化或业务限制变化时，旧意图必须失效。
- 批量状态变更不得用当前页面可见行替代选择快照、筛选快照、权限版本和目标摘要。
- 无权限状态不得泄露当前状态、下一步动作、数量、审批意见、内部状态码或旧缓存。
- 移动端不得删除状态原因、禁用原因、确认、结果回执、审计入口或恢复路径。
- 未实际执行浏览器、键盘、屏幕阅读器、触摸、权限切换、版本冲突、异步任务和移动端视口检查时，必须标为未验证。

## 验收策略

新增 Ruby 结构化审计，验证：

- `SKILL.md` 具备状态流转、生命周期、发布、审批、启停、归档、冻结、锁定等路由关键词。
- `README.md` 和 `HANDOFF.md` 只写摘要和链接，不复制完整 owner。
- `references/status-lifecycle-transitions.md` 包含状态模型、转换意图、结果状态、权限无泄露、审计回执、批量快照、移动端保留和未验证边界。
- RED/GREEN 证据覆盖 badge 伪装流转、loading 伪装成功、缺版本提交、冲突继续覆盖、Toast-only 结果、权限泄露、移动端删恢复和 false verified。
- 全量维护审计、Markdown 相对链接和 `git diff --check` 必须通过后提交并推送。

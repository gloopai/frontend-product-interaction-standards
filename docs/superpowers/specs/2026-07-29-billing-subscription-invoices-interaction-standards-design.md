# 计费、套餐、订阅与发票交互规范设计

## 背景

管理台常见 Billing、订阅、套餐升级/降级、试用、用量额度、付款方式、账单周期、优惠券、发票、支付失败、续费、取消订阅和退款入口。它们经常被做成普通设置页或普通表格：一个套餐卡片、一个“升级”按钮、一个付款方式表单、一个发票下载列表、几个用量条。这个做法很容易出问题：套餐展示价、确认价和实际生效价不一致；保存付款方式被误写成付款成功；支付成功被误写成套餐已生效；降级/取消没有说明失去的能力、数据保留或生效时间；旧发票下载链接在权限变化后继续可用；用量额度延迟没有标注；Toast 成为唯一支付失败恢复；移动端把影响范围和账单周期藏掉。

现有规范已覆盖部分边界：

- `settings-preferences-configuration.md` 负责普通配置草稿、保存、生效值和作用域。
- `risk-actions.md` 负责取消订阅、降级、删除付款方式、退款、敏感导出等高风险确认和未知结果。
- `exports-downloads-artifacts.md` 负责发票、收据、账单明细、对账单等下载产物的身份、权限复核和旧链接失效。
- `async-jobs-task-center.md` 负责支付、开票、退款、同步账单、重新生成发票等异步任务结果。
- `audit-log-activity-history.md` 负责计费变更、支付、发票下载、退款和权限相关的审计证据。
- `permissions-tenancy-visibility.md` 负责账单管理员、租户/工作区切换、只读/无权限和旧入口失效。
- `feedback-states.md` / `global-feedback.md` 负责错误、部分成功、未知结果、Toast 边界和恢复入口。
- `data-tables.md` 负责发票列表、账单记录、用量明细、支付记录、行操作和批量导出。

缺口是：没有 owner 专门负责“商业状态 + 支付状态 + 用量/额度状态 + 发票产物状态 + 生效时间”的一致性。这会导致项目只按普通设置或普通风险动作处理，忽略金额、账期、用量、套餐权益、支付结果和发票下载之间的状态链。

## 目标

- 新增“计费、套餐、订阅与发票” owner，覆盖 plan、pricing、subscription、trial、usage、quota、billing cycle、payment method、invoice、receipt、refund、coupon、credit、renewal、cancel、upgrade、downgrade 和 billing history。
- 明确套餐展示、确认、支付、订阅生效、权益生效、用量更新、发票生成、下载领取、退款处理和审计写入的状态边界。
- 禁止把套餐变更当成普通设置保存、把付款方式保存当成支付成功、把支付成功当成订阅已生效、把用量条当成实时额度证明、把发票链接当成永久权限证明。
- 规定升级、降级、取消、续费、删除付款方式、切换账期、应用优惠、购买额度、申请退款、重新开票和敏感账单导出的权限、租户/工作区、金额快照、请求身份、风险确认和审计绑定。
- 规定旧价格、旧套餐卡片、旧付款方式、旧发票下载链接、旧账单记录、旧用量摘要、旧 Toast/Notification 在权限、租户/工作区、订阅版本、支付结果、账单周期、价格版本或会话变化后失效或重算。
- 规定移动端不得删除金额、账期、税费/折扣摘要、当前套餐、目标套餐、权益变化、失效时间、支付失败恢复、发票下载、审计入口和权限说明。

## 非目标

- 不定义支付网关、银行卡校验、税务计算、定价策略、货币换算、会计规则、发票法规、退款政策、订阅引擎、计量后端、账单同步任务、风控规则、税号验证、收单通道或第三方 provider API。
- 不定义具体套餐名、价格、优惠券规则、额度模型、发票模板、税率、币种支持、国家/地区合规文案或品牌视觉。
- 不替代 `risk-actions.md` 的风险确认；取消订阅、降级、退款、删除付款方式等仍进入 Risk owner。
- 不替代 `exports-downloads-artifacts.md` 的发票/收据/账单下载产物规则。
- 不替代 `async-jobs-task-center.md` 的异步支付、开票、退款或同步任务生命周期。
- 不替代 `permissions-tenancy-visibility.md` 的账单权限、租户/工作区可见性和无泄露规则。
- 不提供财务、税务或法律建议；只定义前端产品交互和验收边界。

## 推荐方案

推荐新增独立 owner：`references/billing-subscription-invoices.md`。

备选方案：

1. **放入设置规范。** 优点是订阅页常像设置页；缺点是金额快照、支付结果、账单周期、权益生效、用量延迟和发票下载不是普通配置状态。
2. **放入风险操作规范。** 优点是取消、降级、退款确实高风险；缺点是计费页还有套餐展示、用量额度、支付失败、发票状态和只读账单记录，不全是危险动作。
3. **独立 Billing owner 协调相邻规范。** 推荐。该 owner 维护商业对象、价格快照、订阅版本、支付状态、用量/额度、发票产物和审计回执；风险动作、下载产物、异步任务、权限和反馈交给已有 owner。

选择独立 owner 的理由：计费事故通常发生在“用户看到的商业承诺”和“系统真实生效状态”不一致。独立 owner 可以把套餐、价格、权益、支付、账期、发票、用量、权限和审计绑定到同一条状态链上。

## 核心规则

### Billing 不是普通设置项

计费、套餐、订阅、付款方式、用量额度和发票不能只按普通设置项展示。套餐展示状态、确认状态、支付状态、订阅生效状态、权益生效状态、用量状态、发票产物状态和审计状态必须分开表达。

付款方式保存成功不等于支付成功；支付成功不等于订阅已生效；订阅已生效不等于所有权益、用量额度、发票和审计都已更新。界面必须说明每一步当前状态和下一步恢复路径。

### 价格、账期和权益必须冻结快照

套餐卡、确认页、支付请求、审计记录和结果回执必须绑定同一个 `pricingSnapshot`。该快照至少包含套餐、价格、币种、周期、税费、折扣、抵扣、试用、按量计费、预估总额、价格版本、租户/工作区和确认时间。

切换套餐、升级、降级、切换月付/年付、应用优惠、购买额度、取消续费或恢复订阅前，必须展示当前套餐、目标套餐、账期、生效时间、权益变化、数据保留、额度变化、费用变化和未知结果处理。旧价格、旧优惠、旧估算、旧套餐卡片和旧确认面板在价格版本、权限、租户/工作区、订阅版本、优惠状态或会话变化后必须失效或重算。

### 支付、订阅和权益状态不能混合

`paymentState`、订阅状态、`entitlementState`、`usageQuotaState` 和 `invoiceState` 必须分开。支付失败、需要 3DS/额外动作、支付处理中、支付未知、订阅待生效、权益同步中、发票生成中和用量延迟不能都显示成一个 loading 或一个成功 Toast。

未知结果不能伪装成支付成功、订阅成功、取消成功、降级成功、退款成功、发票已生成或额度已到账。必须提供检查最新状态、查看账单历史、进入任务中心、重试支付、更新付款方式、联系支持或查看审计路径。

### 取消、降级、退款和删除付款方式是风险操作

取消订阅、取消自动续费、降级套餐、删除付款方式、申请退款、撤销退款、清空余额、购买大额额度、切换账期产生即时收费或失去权益的操作必须进入 `risk-actions.md`。确认前请求数为 0；确认必须说明影响范围、金额、账期、失效时间、权益变化、数据保留、可恢复性、审计回执和未知结果处理。

不得用 Switch/Toggle 直接取消订阅、开启/关闭自动续费、删除付款方式或切换高影响账期。若保留开关视觉，它只能作为打开风险确认承载面的入口。

### 发票、收据和账单下载是受控产物

发票、收据、账单明细、对账单、消费记录和税务资料下载必须执行 `exports-downloads-artifacts.md`。下载链接不是权限证明；每次下载必须复核账单权限、租户/工作区、发票身份、订阅版本、文件有效期、请求身份和审计。

旧发票链接、旧收据链接、旧账单导出任务、旧浏览器历史、旧 Notification、旧复制链接和旧 Toast/Notification 必须在权限变化、会话过期、租户/工作区切换、发票状态变化、退款、作废、重新开票或对象删除后失效或重新证明安全。

### 用量、额度和余额必须说明口径

用量、额度、余额、抵扣、试用剩余额度、超额状态和消费记录必须声明计量周期、刷新时间、数据延迟、估算/最终状态、单位、权限范围和适用套餐。用量条不能作为实时额度证明；延迟、估算、部分同步失败或未知结果必须可见。

购买额度、追加 seats、超额付费、恢复额度和余额抵扣必须说明何时生效、是否可退款、是否影响当前账期、是否可能重复扣费以及如何查看审计。

### 权限、租户和敏感信息不能泄露

无权限用户不得通过套餐卡、价格、折扣、税费、发票列表、支付错误、用量条、账单历史、DOM/ARIA、Toast、Notification、下载链接或审计摘要推断账单主体、付款方式、金额、税号、地址、邮箱、发票编号、内部 ID、支付 provider 对象或旧缓存。

权限、租户/工作区、会话、订阅版本、价格版本、付款方式版本、发票状态、退款状态或账单账户变化后，旧套餐卡、旧确认面板、旧支付按钮、旧付款方式、旧发票链接、旧用量摘要、旧 Toast/Notification、旧审计跳转、旧焦点目标和旧 ARIA 引用必须失效或重算。

### Toast 和 Notification 不能是唯一回执

支付失败、支付未知、取消订阅、降级、退款、发票生成失败、发票下载失败、用量同步失败、权限拒绝和部分成功不能只靠 Toast、Notification、Snackbar 或浏览器提示表达。页面内必须有账单状态、订阅状态、付款恢复、任务入口、发票入口、审计入口或支持路径。

### 移动端能力不能丢

移动端不得删除当前套餐、目标套餐、金额、币种、账期、税费/折扣摘要、权益变化、用量口径、额度状态、付款方式状态、支付失败恢复、取消/降级影响范围、发票下载、账单历史、审计入口、权限说明和恢复路径。

低高度、虚拟键盘、安全区域、系统字体放大、浏览器 Back、WebView 返回、支付额外认证跳转和触摸长按后，金额、确认按钮、取消路径、错误摘要、账期说明、支付恢复和审计入口仍必须可达。

## 与其他 owner 的关系

- `settings-preferences-configuration.md`：负责普通配置草稿、保存和生效值；本 owner 负责商业状态、金额快照、支付、订阅、权益、用量和发票状态。
- `risk-actions.md`：负责取消、降级、退款、删除付款方式、切换账期、购买大额额度等风险动作的确认、请求身份和未知结果。
- `exports-downloads-artifacts.md`：负责发票、收据、账单明细、对账单和消费记录下载产物的身份、权限复核、有效期和旧链接失效。
- `async-jobs-task-center.md`：负责支付处理中、开票中、退款中、账单同步、发票重新生成和用量同步等后台任务。
- `audit-log-activity-history.md`：负责套餐变更、支付、取消、降级、退款、开票、下载和失败恢复的审计证据。
- `permissions-tenancy-visibility.md`：负责账单权限、租户/工作区、无权限、只读、隐藏入口、禁用原因和旧缓存清理。
- `data-tables.md`：负责发票列表、账单历史、支付记录和用量明细的表格行为；本 owner 规定金额、状态和下载边界。
- `auth-session-reauth.md`：负责高风险付款、删除付款方式、退款或查看敏感账单信息前的重新认证。
- `global-feedback.md` / `feedback-states.md`：负责反馈通道；本 owner 规定 Toast/Notification 不能成为唯一回执或泄露敏感账单信息。

## 验收策略

后续实现新增静态审计 `docs/testing/billing-subscription-invoices/billing-subscription-invoices-audit.rb`，检查：

- `SKILL.md` 有计费、账单、套餐、订阅、发票、支付、用量、额度、退款、优惠券等路由。
- `references/billing-subscription-invoices.md` 存在并包含 `billingSubscriptionState`、`pricingSnapshot`、`paymentState`、`invoiceState`、`usageQuotaState`、价格/账期/权益快照、风险动作、发票下载、旧链接失效、权限无泄露、Toast 边界、移动端恢复和未验证边界。
- README / HANDOFF 有中文摘要。
- RED/GREEN 证据覆盖普通设置项、付款方式保存伪装支付成功、支付成功伪装订阅生效、套餐价格未冻结、取消订阅用 Switch 直接执行、发票链接旧权限可用、用量条无口径、支付失败 Toast-only、未知结果伪装成功、无权限泄露金额或发票、移动端删除金额/账期/恢复路径等负例。
- mutation 模式删除任一关键规则会失败。

运行时真实浏览器、移动端设备、屏幕阅读器、真实支付 provider、真实支付额外认证、真实发票下载、真实退款/取消/降级任务、真实权限切换、真实会话过期、真实账单同步和真实审计写入未执行时，必须标为**未验证**，不能把静态审计写成运行时通过。

## 设计取舍

这个 owner 的边界有意停在前端产品交互层：不定义支付通道、不定义税费算法、不定义套餐价格，也不替项目写财务规则。它强制前端证明每一次展示价格、确认订阅、保存付款方式、发起支付、取消降级、生成发票、下载账单和查看用量都绑定同一个账单主体、订阅版本、价格快照、权限版本、请求身份和审计回执。这样能防住管理台里最常见的计费事故：用户以为支付了、升级了、取消了、发票拿到了或额度到账了，但真实商业状态和界面回执并不一致。

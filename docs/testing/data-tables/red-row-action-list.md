# 管理列表设计说明

## 1. 能力边界

该列表采用“首屏加载 + 游标续载”的模型，不模拟页码分页。

- 支持首次加载、手动刷新、加载下一段、重试、返回列表后的状态恢复。
- 不支持随机跳到第 N 页；除非后端额外提供可寻址游标。
- 不展示“共 N 条”，除非后端返回可靠总数；客户端已加载数量不能冒充总数。
- 游标、排序和数据快照的一致性由后端契约保证。客户端只能去重和阻止明显的重复游标，无法彻底避免后端数据变动造成的漏项。
- 前端权限只用于展示和交互控制，不能作为安全边界；每个行操作仍须由服务端再次鉴权。
- 行菜单是命令菜单，不承担行选择、多选或单元格编辑职责。
- 默认不引入虚拟滚动。若数据规模要求虚拟化，应另行设计焦点保留、菜单锚点、读屏顺序和卸载策略。
- 高风险操作不得在菜单项点击后立即不可逆执行，应进入与风险等级相符的确认流程。
- 请求被浏览器中止不等于服务端操作已取消；写操作的最终结果必须由服务端幂等键、查询状态或后续刷新确认。

## 2. 数据与实例模型

每行必须具有跨刷新稳定、不可复用的 `rowId`。禁止使用数组下标作为 React key、菜单锚点或焦点恢复标识。

建议列表实例维护：

```ts
type ListState = {
  phase:
    | "idle"
    | "initial-loading"
    | "ready"
    | "empty"
    | "initial-error"
    | "disposed";
  generation: number;
  rows: Row[];
  nextCursor: string | null;
  isRefreshing: boolean;
  refreshError: ErrorInfo | null;
  isAppending: boolean;
  appendError: ErrorInfo | null;
};

type OpenMenu = {
  rowId: string;
  triggerId: string;
  focusedActionId: string | null;
} | null;
```

每次改变查询条件、排序或执行从头刷新，都递增 `generation`。任何响应提交到界面前必须同时验证：

- 列表实例尚未 disposal；
- 响应所属 `generation` 仍是当前代；
- 请求 ID 仍是该操作通道的当前请求。

分页合并按 `rowId` 去重，并保持服务端返回顺序。若发现 `nextCursor` 与当前游标相同，停止自动续载并显示可重试的协议错误，防止无限请求。

## 3. 列表状态转换

### 首次加载

```text
idle → initial-loading
initial-loading → ready
initial-loading → empty
initial-loading → initial-error
```

首次加载时保留表头和列表区域的稳定位置，显示可见的“正在加载列表”文本。骨架仅作为视觉辅助，并对辅助技术隐藏。不得只显示无名称的转圈图标。

首次失败时不伪造空状态，显示独立错误页内状态：

- 简明错误说明；
- “重试”按钮；
- 必要时提供错误编号或排障入口；
- 不把技术异常堆栈直接展示给用户。

### 刷新

```text
ready/empty → refreshing（旧数据保留）
refreshing → ready/empty（成功后原子替换）
refreshing → refresh-error（旧数据保留）
```

刷新失败时继续展示上一次成功数据，并在列表上方显示非阻断错误条：

> 未能刷新，当前显示的是上次成功加载的结果。

同时提供“重试刷新”。刷新失败绝不能把已有列表替换成空状态。

刷新成功后：

- 从首游标重新建立结果集；
- 清除旧的续载错误；
- 重置 `nextCursor`；
- 原子替换数据，避免用户短暂看到旧新两份结果；
- 通过礼貌型状态区宣布“列表已更新，当前显示 N 项”，其中 N 只是当前已加载数量。

刷新开始时若正在续载，应中止或失效旧续载请求。刷新完成前禁用重复刷新，但列表中仍有效的操作不必整体冻结。

### 加载下一段

```text
ready → appending
appending → ready（合并新行）
appending → append-error（原列表保留）
```

续载失败只影响“加载更多”区域，不覆盖整个列表。保留相同 `nextCursor`，允许用户原地重试。

当后端返回“游标失效”时，不自动循环重试。显示：

> 数据位置已过期，请从头刷新列表。

用户确认刷新后才清空旧游标链。若需要返回详情后恢复列表，应在路由状态或列表缓存中保存查询、已加载行、游标、滚动位置和聚焦行；不能把不可公开或过长的游标无条件写入 URL。

### 空状态

空状态至少区分：

- 数据源确实没有内容：说明尚无记录；用户有创建权限时提供创建入口。
- 筛选后无结果：说明当前条件无匹配项，并提供“清除筛选”。
- 刷新失败：不是空状态，仍展示旧数据。
- 权限导致不可见：不得暗示数据不存在；根据产品安全策略显示通用无权限说明或由路由级权限页处理。

## 4. 行菜单与权限变化

每行最多呈现一个明确命名的操作触发按钮，例如视觉上为省略号，但可访问名称必须是“打开〈对象名称〉的操作菜单”。

菜单规则：

- 同一列表实例一次只允许打开一个行菜单。
- 菜单与 `rowId` 绑定，不与当前数组位置绑定。
- 菜单打开后，普通刷新重渲染不得导致它无故关闭；同一行仍存在时重新锚定到新的触发节点。
- 行被刷新结果移除时关闭菜单，并执行焦点降级策略。
- 无任何可用操作时不显示空菜单；操作列显示“无可用操作”或保留非交互占位。
- 未授权操作不展示。
- 已授权但因当前行状态暂不可执行的操作可以禁用，同时以可见文本或可访问描述说明原因，不能只依赖灰色。
- 权限尚未确定时不得先按“允许”呈现；可以显示权限加载状态，但不能让未知权限的操作可执行。

权限在菜单打开期间变化时：

1. 原子更新当前行的动作集合。
2. 若被移除的不是当前焦点项，保留当前焦点。
3. 若当前焦点项被移除，将焦点移到相邻的下一个可用项；没有下一个则移到上一个。
4. 若菜单已无可用项，关闭菜单并把焦点移到该行仍存在的主要入口；若该入口也不存在，则移到相邻行或列表标题。
5. 不把焦点落到已移除、隐藏或禁用节点。
6. 通过礼貌型状态区宣布“可用操作已更新”。

用户触发操作时再次请求服务端鉴权。若返回 `403` 或等价权限变化响应：

- 不自动重试写操作；
- 关闭或更新菜单；
- 显示行级错误“权限已变化，无法执行此操作”；
- 刷新该行权限或列表；
- 焦点按上述策略恢复；
- 服务端错误详情写入日志，但不向用户泄露敏感权限信息。

若操作请求已发出后权限发生变化，客户端不能仅凭本地权限事件假设操作已取消；等待服务端结果或把结果标记为未知并刷新确认。

## 5. 键盘操作

### 菜单触发按钮

- `Enter`、`Space`：打开菜单并聚焦第一个可用菜单项。
- `ArrowDown`：打开并聚焦第一个可用菜单项。
- `ArrowUp`：打开并聚焦最后一个可用菜单项。
- 已打开时再次激活触发按钮：关闭菜单并保留焦点在触发按钮。

### 菜单内部

- `ArrowDown` / `ArrowUp`：在可用项之间循环移动。
- `Home` / `End`：移动到第一个 / 最后一个可用项。
- `Enter` / `Space`：执行当前项。
- `Escape`：关闭菜单并恢复到有效的触发按钮或降级目标。
- `Tab` / `Shift+Tab`：关闭菜单，并继续到触发按钮之后 / 之前的正常页面焦点项；菜单不是焦点陷阱。
- 可实现按首字符查找，但必须正确处理本地化文本，不能影响输入法组合输入。

点击菜单外部时关闭菜单，但不得强制把焦点抢回旧触发按钮，因为用户可能已经点击了另一个控件。

禁止仅依靠 Hover 打开菜单。Hover 可以提供视觉反馈，但点击、触摸和键盘路径必须完整。

## 6. 焦点管理

实现一个独立的焦点协调器，以逻辑标识而非临时 DOM 引用保存返回意图：

```ts
type FocusToken = {
  routeInstanceId: string;
  listInstanceId: string;
  rowId: string;
  control: "row-action" | "row-primary";
};
```

恢复焦点前必须确认：

- 路由实例仍相同；
- 列表尚未 disposal；
- 对应行仍存在；
- 目标可见、可聚焦且未禁用。

推荐降级顺序：

1. 同一行的操作触发按钮；
2. 同一行的主要链接或名称；
3. 下一行的主要入口；
4. 上一行的主要入口；
5. 列表标题或带 `tabindex="-1"` 的列表区域。

不同关闭原因采用不同策略：

- `Escape`：恢复触发按钮或降级目标。
- 点击外部：尊重用户点击产生的新焦点，不恢复旧触发按钮。
- 选择导航操作：由新路由负责焦点，旧列表不恢复。
- 打开确认界面：由确认界面接管焦点。
- 内联操作成功且行仍存在：键盘用户回到该行触发按钮，并宣布结果。
- 操作成功后行被移除：移动到相邻行主要入口；列表为空则移动到空状态标题。
- 路由卸载：取消所有旧焦点恢复，不得把焦点送回即将移除的元素。

数据加载本身不自动抢焦点。若用户通过“重试”恢复首次错误，而重试按钮随后被成功内容替换，应在内容提交后把焦点移动一次到列表标题或列表区域。若“加载更多”按钮仍存在，成功后保留焦点在该按钮；若已无下一页导致按钮移除，则移动到第一条新加载记录的主要入口，或“已加载全部内容”的状态节点。

## 7. ARIA 与语义

桌面表格使用原生 HTML：

- `<table>`、`<caption>` 或由 `aria-labelledby` 关联的可见标题；
- `<thead>`、`<tbody>`；
- 列标题使用 `<th scope="col">`；
- 行标题在适合的数据模型下使用 `<th scope="row">`；
- 操作列有可感知列名，例如“操作”。

不要给普通浏览表格添加 `role="grid"`。只有真正实现完整二维网格键盘模型时才使用 Grid 模式。

操作触发按钮：

```html
<button
  aria-label="打开订单 A-1024 的操作菜单"
  aria-haspopup="menu"
  aria-expanded="true"
  aria-controls="row-menu-a1024">
</button>
```

菜单：

- 容器使用 `role="menu"`，并以对象名称提供可访问名称；
- 项使用 `role="menuitem"`；
- 采用 roving `tabindex`，同一时间只有当前项为 `0`；
- 暂不可用项使用 `aria-disabled="true"`，并阻止激活；
- 分组确有语义时才使用 `role="separator"`；
- 危险性、成功、失败和禁用原因不能只通过颜色表达。

仅在完整实现上述键盘行为时使用 `menu/menuitem`；否则应使用普通按钮列表语义，不能只贴 ARIA 角色而不实现对应交互。

列表区域在请求期间使用 `aria-busy="true"`，但已有内容仍可读取。加载与成功消息通过单一 `role="status"`、`aria-live="polite"` 区域宣布。用户主动操作失败可使用可见的 `role="alert"`，避免同时触发多个重复播报。

菜单浮层通过 Portal 渲染时，触发器与菜单 ID 仍须唯一稳定。菜单不得被裁剪在表格滚动容器内。

## 8. 桌面与移动端适配

断点由内容可用性决定，不按设备型号决定。

### 桌面

- 使用语义表格。
- 对象身份、状态和主要操作优先展示。
- 操作列位置稳定，菜单进行视口碰撞检测；空间不足时向上或横向翻转。
- 横向滚动仅用于数据比较确实需要的表格，关键身份和操作入口必须仍可定位。

### 窄屏与移动端

当表格无法在 200% 缩放下保持可用时，转换为卡片列表：

- 列表使用 `<ul>`/`<li>` 或等价列表语义；
- 每张卡片保留对象名称、关键状态、错误信息和全部操作入口；
- 字段以清楚的“标签—值”关系呈现；
- 行操作按钮仍位于可发现位置，不能因移动端空间不足删除；
- 菜单仍支持触摸、点击和键盘，不依赖长按；
- 触摸目标建议至少 `44×44 CSS px`，相邻目标保持足够间距；
- 浮层考虑四向安全区域、动态浏览器工具栏和低高度视口；
- 菜单内容过长时内部受控滚动，当前焦点项必须滚入可见区域。

桌面表格与移动卡片不得同时以可访问形式存在。断点实时变化时保持同一个逻辑列表和同一个菜单实例：

- 查询、游标、已加载行、滚动上下文和操作请求不重置；
- 菜单仍按同一 `rowId` 锚定；
- 原触发节点被布局转换替换时，只把焦点移动一次到等价的新触发节点；
- 不创建重复 Portal、监听器或请求。

必须兼顾窄屏、低高度、横屏、系统字体放大、长文本、国际化扩展、虚拟键盘、四向安全区域和 200% 浏览器缩放。核心流程不得要求双向滚动。

## 9. 请求并发与错误归属

为不同请求通道分别保存控制器和请求 ID：

- 首次加载 / 从头刷新；
- 游标续载；
- 行权限刷新；
- 每个行操作；
- 可选预取。

约束如下：

- 同一通道只接受最后一个有效请求结果。
- 刷新优先于续载；开始刷新时失效当前续载。
- 同一行同一操作提交期间禁用重复触发。
- 不因某一行操作失败把整个列表切换为错误状态。
- 行操作失败显示在对应行或后续确认界面，并提供适当重试路径。
- 网络超时与业务拒绝分开处理；业务拒绝不得自动重放。
- 写请求建议使用幂等键，避免超时重试导致重复执行。
- 所有异步回调在更新 UI 前检查实例、代次和请求 ID。

## 10. Disposal

路由变化或拥有列表的组件卸载时，从任何状态立即进入终态 `disposed`，不等待菜单退出动画，也不再接受刷新、续载、菜单打开或新行操作。

处置顺序：

1. 设置 `disposed = true` 并递增实例代次，使所有旧回调立即失效。
2. 阻止新的事件处理和请求创建。
3. 中止或失效首次加载、刷新、续载、权限、预取和安全可取消的行请求。
4. 对已经发出的写请求：
   - 可以中止客户端等待；
   - 不把中止解释为服务端撤销；
   - 丢弃旧页面 UI 回调和 Toast；
   - 只有显式转交给全局操作管理器时才允许跨路由继续展示状态。
5. 取消重试定时器、防抖、节流、`requestAnimationFrame`、延迟聚焦、微任务后的 DOM 操作和动画完成回调。
6. 解除权限订阅、路由订阅、媒体查询监听、窗口与滚动监听、外部点击监听、键盘监听。
7. 断开 `ResizeObserver`、`IntersectionObserver`、菜单定位器的自动更新器及其他观察器。
8. 立即移除该实例拥有的菜单 Portal，不播放退出动画。
9. 取消所有焦点恢复任务；旧路由不再调用 `focus()`。
10. 释放该实例持有的其他资源，例如缓存订阅、浮层层级登记和状态播报节点。
11. 清理函数必须幂等；重复调用不得重复释放或影响其他仍存活实例。

菜单为非模态浮层，通常不应持有页面滚动锁或背景隔离。若所选组件库意外添加了这些资源，必须以实例 ID 引用计数，并且只释放本实例拥有的份额。

新路由提交后，由新路由自己的焦点策略把焦点移动一次到页面主标题、主内容容器或首个主要操作。旧列表不得参与该决定。

## 11. 尚未通过真实运行环境验证的边界

以下内容目前只能作为实现契约，尚未在真实浏览器、组件库、路由和后端环境中验证：

- 后端游标是否提供稳定排序、快照一致性、过期标识，以及数据插入或删除时是否会漏项或重复。

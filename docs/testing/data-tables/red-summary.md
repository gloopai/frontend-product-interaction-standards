# 数据表格规范 RED 基线汇总

## 基线条件

- 运行时 `references/data-tables.md` 不存在，`SKILL.md`、`README.md` 与 `HANDOFF.md` 也没有完整表格 owner 路由。
- 三个场景均由 `fork_turns=none` 的新鲜代理独立完成；提示词没有提供目标 owner、预期答案或基线诊断。
- 每份场景文件都保留完整 prompt、派发参数、逐字原始输出与 completion receipt。
- canonical identities：
  - `/root/table_task1_red/red_display_report`
  - `/root/table_task1_red/red_row_action_list`
  - `/root/table_task1_red/red_bulk_action_table`

## 结论

RED 并不表示三份输出整体不可用。三份独立输出在刷新失败保留旧数据、普通表格使用原生语义、移动端不删除能力和卸载后禁止旧焦点恢复等方面出现明显收敛。

真正的 RED 是：没有表格 owner 时，规则只能由场景局部推导，三份输出没有共同的能力档位、查询快照结构、选择失效矩阵和分页契约；其中单行操作场景还把游标分页设计为“加载下一段”，与本阶段确认的“上一页/下一页游标分页、不包含加载更多”范围直接分歧。Tasks 2–3 必须把这些场景内判断提升为同一个、可执行验收的 owner 契约。

## brief 要求的逐项核对

| 核对项 | RED 实际输出 | 基线判断与后续约束 |
| --- | --- | --- |
| 只读报表是否错误出现选择列 | 展示型输出明确排除行选择和批量操作；单行操作输出也明确行菜单不承担选择。 | 本次没有误加选择列，但结论只来自场景文字，没有共享能力声明。Task 2 需定义 `display`、`row-action`、`bulk-action` 三档并禁止降级后遗留空选择列或工具栏。 |
| 筛选草稿与已应用条件是否分离 | 展示型输出明确使用 `draftFilters` 与 `appliedQuery`；批量输出只有 `queryKey`、`queryToken` 与筛选变化规则；单行操作输出未建立筛选草稿模型。 | 仅展示型场景覆盖，跨场景未收敛。Task 2 需统一即时应用、显式应用、默认重置和已应用条件可见性。 |
| 排序是否包含稳定次序键 | 展示型输出给出“业务排序字段 + 唯一字段”并要求快照；单行操作输出只把稳定排序和快照一致性交给后端契约；批量输出只说明排序如何进入 `pageKey`/`queryKey`。 | 只有展示型输出完整回答稳定次序键。Task 2 需把稳定次序键、空值/区域规则和跨页无重复遗漏变成所有分页模式的硬规则。 |
| 翻页、筛选和排序是否改变选择 | 批量输出规定：筛选成员条件变化清除选择；页级选择遇到分页、页大小或排序变化清除；全部筛选结果在成员集合不变时可跨翻页和普通排序保留。其他两场景没有选择状态。 | 批量场景内部较完整，但缺少 owner 级事件矩阵。Tasks 2–3 需明确查询快照先变化，再按选择范围清除、保留或要求重新确认。 |
| “当前页全选”是否被误解为全数据集全选 | 批量输出明确写出两者不是同一能力，表头复选框只描述当前页，并用独立按钮提升到全部筛选结果。 | 没有误解。Task 3 仍需把当前页三态、不可选择项计数和显式二次提升写成可执行验收。 |
| 跨页选择是否绑定查询快照和排除项 | 批量输出要求服务端 `queryToken`、`queryKey`、`excludedIds`、总数和有效期，并禁止单一 `allSelected=true`。 | 已覆盖，但术语和失效条件只存在于该场景。Task 3 需固化查询快照、筛选范围、排除项、展示数量和重新确认规则。 |
| 刷新失败是否保留旧数据 | 三份输出都明确保留上一次成功结果、标记过期或“可能不是最新”，并提供重试。 | 三个场景已收敛。Task 2 应把“首次失败替换不可用结果、刷新失败保留旧数据”固化为共同状态机和结果区域错误 owner。 |
| 部分成功是否保留失败项及重试 | 批量输出保留逐项失败明细，区分可重试、不可重试、跳过和未知，并且只用可重试失败 ID 创建新尝试，不重复成功项。 | 已覆盖；接受任务后清除表格选择、失败集合由独立任务状态持有。Task 3 需明确选择快照与操作快照的边界，并验收全部成功、部分成功、全部失败、权限和版本冲突。 |

| route/unmount 后旧响应和焦点是否仍生效 | 单行操作与批量输出均定义 `disposed`、实例/generation 校验、幂等资源释放和禁止旧焦点恢复；展示型只要求取消请求、防抖与焦点任务，没有完整实例隔离与迟到回调提交门槛。 | 两个管理场景覆盖充分，展示型明显较弱。Task 3 需让所有能力档位统一失效旧查询、菜单、操作、公告和焦点回调，并验收两实例隔离。 |

## 额外真实分歧

1. **游标分页形态不一致**：单行操作输出采用“首屏加载 + 加载下一段”，包含 `appending` 和“加载更多”；确认设计只支持上一页/下一页游标分页，并明确排除加载更多和无限滚动。Task 2 必须消除该直接分歧。
2. **能力声明不统一**：三份输出凭任务名称分别推断只读、行操作和批量能力，没有共同枚举、权限降级或空工具栏规则。Task 2 必须建立显式档位。
3. **查询状态命名与边界不统一**：展示型使用 `draftFilters`、`appliedQuery`、`requestId`、`snapshotId`；单行操作使用 `generation`、请求通道和游标；批量使用 `pageKey`、`queryKey`、`queryToken`。Task 2 需要定义共同不可变查询快照和请求代次，再允许分页模式的必要差异。
4. **分页后的焦点策略不统一**：展示型页码分页成功后主动聚焦结果标题；单行操作续载通常保留“加载更多”焦点；批量场景按行移除和任务状态决定焦点。owner 应按事件、触发来源和目标是否仍存活定义可预测策略，而不是用单一全局动作。
5. **运行时证据边界一致但尚未执行**：三个代理都明确列出浏览器、屏幕阅读器、触摸、200% 缩放、真实后端竞态和 disposal 资源计数尚未在真实环境验证。后续文档检查不得把这些静态设计判断写成运行时通过。

## Tasks 2–3 的最小闭环

- Task 2：能力档位；四组状态；查询快照与请求代次；筛选草稿/已应用条件；稳定排序；页码与上一页/下一页游标分页；首次加载、刷新、空状态与错误；列行为；原生 Table/Grid；焦点恢复和可执行验收。
- Task 3：当前页三态；可选全部筛选结果；查询范围、排除项与重新确认；不可变操作快照；全部/部分/全部失败及权限/版本冲突；响应式等价；200% 与移动端；route/unmount disposal、迟到回调、实例隔离和可执行验收。
